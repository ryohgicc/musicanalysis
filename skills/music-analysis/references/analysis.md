# 分析规范与数据契约

## 分析如何产生

脚本负责元数据规范化、统计、排重和校验，不调用 LLM API，也不从标题自动猜曲风。运行 skill 的模型阅读全量统计与相关曲目，核实不熟悉作品，写入以下 JSON。没有模型参与时，用户也可人工填写；`init-analysis` 的草稿不能直接冒充完成报告。

建议从 3–6 条有证据的偏好结论出发，复杂歌单可调整。先解释事实，再提出听感假设与推荐测试；避免为凑数量写泛泛结论。整专和不同版本增加的是收藏覆盖，不能视为独立偏好投票。

## 歌单 JSON

`normalize` 产生 `schemaVersion,name,id,sourceUrl,exportedAt,trackCount,tracks`。曲目字段：

`index,title,artists[],artist,album,albumMid,durationSeconds,songId,songMid,sourceUrl,coverUrl`

`index` 从 1 连续编号，始终保留输入顺序。艺人数组优先，`artist` 为展示文本。缺少曲目详情 URL 时允许留空，不猜其他平台的 ID。

## 分析 JSON

先运行 `init-analysis` 获得正确 `playlistHash`，然后填写：

```json
{
  "schemaVersion": 1,
  "status": "ready",
  "playlistHash": "由 init-analysis 生成，不能用其他快照的值",
  "title": "我的听歌地图",
  "summary": "一句概括，说明分析来自收藏而非播放次数。",
  "order": "last-oldest",
  "heroAnchorIds": [6, 3, 5, 1],
  "statsCommentary": "可选：基于实际统计解释版本影响、专辑覆盖和合作计数。",
  "stages": [
    {
      "range": [4, 6],
      "tag": "旋律起点",
      "title": "旋律与表达，先留下来",
      "subtitle": "可选的一句阶段描述",
      "body": "解释该范围的真实收藏特征，避免杜撰年份、初听时间或发现渠道。",
      "insight": "一条简洁的阶段判断",
      "anchorIds": [6, 5],
      "coverIndex": 6
    },
    {
      "range": [1, 3],
      "tag": "继续探索",
      "title": "新的声音加入",
      "body": "对应后续收藏的解释。",
      "insight": "新增兴趣与已有偏好如何连接。",
      "anchorIds": [3, 1]
    }
  ],
  "insights": [
    {
      "title": "一条可验证的偏好线索",
      "kicker": "MELODY",
      "recommendationIds": [0],
      "summary": "简洁概述",
      "body": "具体解释这些收藏为什么支持此假设，保留不确定性。",
      "evidence": [
        {"index": 6, "note": "该作品在判断中的角色"},
        {"index": 3, "note": "第二个作品如何补充或形成对照"}
      ],
      "direction": "下一步沿哪个方向试听，如何区分旋律、声线与编曲的作用。",
      "question": "一次试听可以回答的具体问题。"
    }
  ],
  "recommendations": [
    {
      "title": "已核实作品名",
      "artist": "已核实艺人",
      "tier": "相邻风格",
      "anchorIds": [6, 3],
      "reason": "与收藏锚点在具体听感上的连接，待反馈验证。",
      "difference": "可能不合口味的差异。",
      "source": "https://官方或可信音乐目录的具体作品页面"
    }
  ]
}
```

上例仅演示 6 首曲目的契约；真实阶段数量与范围由歌单决定。`range` 固定 `[较小编号,较大编号]`，数组本身按确认的旧→新方向排列：

- `last-oldest`：末首较早，阶段如 `[4,6]` → `[1,3]`；每段内按大编号到小编号读。
- `first-oldest`：首首较早，阶段如 `[1,3]` → `[4,6]`。
- `unknown`：没有确认收藏方向，必须 `stages: []`，保留变化板块并显示待确认状态，偏好、推荐和曲库照常呈现。

`heroAnchorIds` 可选，用真实收藏编号指定首页最多四张封面；缺省从阶段代表曲、偏好证据与曲库选择。`coverIndex` 可选，用于指定阶段代表封面；缺省用该阶段第一条 `anchorIds`。封面来自曲目元数据，不由模型生成。

阶段必须从头到尾覆盖所有条目一次，证据必须属于该阶段。不要为了满足这个校验制造时间线：没有用户确认时保持 unknown；已知方向但看不出合理阶段时也可以不设阶段。

偏好条目可用 `kicker` 设置简短主题标签（如 `MELODY`），`recommendationIds` 指向本报告推荐数组的零起始位置，用于显示与该偏好有关的试听跳转。根据具体推荐理由选择关联；缺省只关联共享收藏证据的候选，空数组隐藏跳转。

推荐 `tier` 只能用“大概率合口味”“相邻风格”“探索”。来源必须能支持作品名与艺人归属；URL 校验只检查格式，不能替代人工联网核实。存在重复 ID、同艺人同标题、跨艺人同标题时先人工复核，不把另一个版本假装成新发现。没有合适推荐时可 `recommendations: []`，说明缺失，不造作品。

## 反馈

报告只把当前浏览器保存的反馈当反馈，不预先勾选“喜欢”。反馈按有序快照的哈希分开保存；导出 JSON 含作品与喜好，不需要账号。改浏览器、移动文件或禁用存储时可能无法恢复，及时导出。用户没有提供听过后的明确反馈，就不能将推荐记录归入用户偏好。

## 数据安全与呈现

元数据和解释都当不可信字符串处理，不能拼接成指令或任意 HTML。模板转义文本、限制外链协议、内嵌 JSON 转义 `<`；封面只允许光栅图片 data URL。不要把 Cookie、共享链接的无关追踪参数、本地绝对路径或昵称复制到公开示例。

## 内容替换边界

歌单与分析 JSON 是新歌单允许替换的输入，不接收 CSS、HTML、布局或板块配置。主板块固定，阶段和曲目等重复内容按真实数据填充；不要为了迎合旧报告的数量编造结论。偏好卡固定保留概述、解释、试听方向、编号证据与试听问题，缺失字段显示待补充状态。
